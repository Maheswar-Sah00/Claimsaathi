Guided walkthrough
Welcome

Let’s walk through ClaimSaathi together.

You’ll play Arjun, whose father Ramesh is in hospital. In about five minutes you’ll check his claim, send a missing document, and see how the agent handles consent, tricky statuses and portal timeouts.

Before you start
  • The mock TPA portal is running at {{ portal }}.
  • This agent is running (you’re looking at it).
  • Optional: run .\scripts\reset_demo.ps1 for clean demo data.

Each step has a Try it button that opens the real page in a new tab, so this guide stays open here. Use ← → or the buttons below to move.

Ask

Ask: “Where is my father’s claim?”

  1. On the Dashboard, keep policy POL-HDF-778812.
  2. Enter claim CLM-2026-0142.
  3. Choose Status, and send missing documents and press Check claim.
What happens behind the scenes

Before anything else, the agent checks consent: Ramesh has allowed Arjun to read the status and upload documents for this claim. Without that, the agent would stop here and never open the portal.

Try it: open dashboard ↗
Portal OTP

The agent pauses. You type the OTP.

The agent logs in to the TPA portal and stops at the OTP screen. Your claim page shows the portal’s own OTP screen.

  1. Find the 6-digit code in the portal’s simulated SMS panel.
  2. Type it on the claim page. The run continues by itself.
Why a person?

The agent is never allowed to read or fill an OTP. A wrong code is refused and you are asked again, a limited number of times.

Read and match

It reads the claim and checks your documents.

The raw status “Query Raised” becomes QUERY_RAISED using a fixed rule table, not an AI guess. Two documents are pending, and each one is checked against Arjun’s document vault:

RequestResultWhy
REQ-0142-01 pharmacy invoiceMATCHED pharmacy_invoice_ramesh.pdf: right patient, dated within 14–18 Oct, readable. Lakshmi’s invoice and an August invoice are refused.
REQ-0142-02 indoor case papersHospital On cashless claims the hospital sends these (IRDAI Master Circular 2024, Ch. I para 17(c)). A note to the hospital is drafted instead.
Approve

Nothing is uploaded until you say yes.

The run pauses again and shows an approval card:

  • Patient, claim and the exact request it answers
  • The file name and a preview
  • Its fingerprint (SHA-256) and every check that passed

Press Approve and upload, or Reject. If anything on the card changes before you press, the approval is refused, so you approve exactly what you saw.

Verify and answer

It checks the upload actually landed.

After uploading, the agent re-reads the portal’s document list. Only when the same file is listed under the same request does it show VERIFIED.

Then you see the answer:

  • Status card with the raw portal text and its last-updated time in IST
  • Documents table: invoice received and verified; case papers for the hospital
  • One next step: send the drafted note to the hospital
  • Agent trace tab: every step, its decision, and evidence screenshots you can open
Consent

Now try your mother’s claim.

  1. From the dashboard, check CLM-2026-0150 (Lakshmi’s claim).
  2. It stops with NEEDS_CONSENT. The portal is never opened: no login, no OTP.
  3. A consent request goes to Lakshmi. Sign out, sign in as Lakshmi, and open Consent to approve it, give fewer permissions, pick 1/7/30 days, or deny.
Try it: open dashboard ↗ Consent page ↗
Honest status

“Approved” that isn’t.

Check CLM-2026-0163. The portal shows pre-authorisation APPROVED Rs 50,000, but the claim itself is Pending Final Authorisation.

ClaimSaathi reports UNDER_REVIEW and shows the pre-auth in a separate card. The status rules only read the claim status, and a reply guard blocks words like “approved”, “settled” or “paid” unless the real status allows them.

Try it: open dashboard ↗
Timeouts

The portal saves the file but never replies.

  1. Reset the demo data (.\scripts\reset_demo.ps1 and the portal’s Reset demo data).
  2. On the portal’s /admin page, set fault timeout_after_store.
  3. Repeat steps 2–5 for CLM-2026-0142.

The upload shows UNKNOWN (not failed, not done). The agent re-reads the list, finds the file and marks it VERIFIED: one upload, no duplicate. If the file had been missing, it would ask you before retrying.

Done

That’s the whole flow.

What you just saw, in one line each:

  • Consent first, checked again before every read and upload.
  • A person types every OTP and approves every upload.
  • Fixed rules, not AI, decide status, matching and upload state.
  • Proof before “done”: only a fresh portal read marks an upload verified.
  • No duplicates: timeouts and crashes re-read instead of re-sending.
  • Everything on record: screenshots, page hashes, decisions and steps.
